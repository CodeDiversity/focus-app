**Why conflict detection is merged into the engine (EP06C) rather than split out.** The epic's proposed story 4 ("calendar conflict detection") is not an independently testable outcome of its own: the conflict rules *are* the engine's placement primitives (the free-interval computation), and the same rules are re-used verbatim by the save-time re-check in EP06D. Splitting them would create a pure-function-to-pure-function dependency with no outcome that can be verified without the engine anyway. The rules are still specified, tested and owned as first-class content of EP06C (the conflict rules section of the shared contract below, TR-E06-03, TR-E06-04). **The "specified once, used twice" claim is held by one named helper:** `freeIntervals(...)` in `apps/api/src/domain/study-planning/intervals.ts` (EP06C) — its complete signature and semantics are in *The shared free-interval helper* below. EP06C's placement calls it with `base: { kind: 'declared', windows }` (the student's declared available windows) and passes the sessions it has already placed in the helper's **`placed`** input; EP06D's save-time re-check calls **the same function** with `base: { kind: 'whole-day' }` (a manual edit is not bounded by the declared availability — D06-12) and passes the **other submitted sessions** in `placed`. There is no second implementation of "available − blocked − classes − confirmed − already placed" to drift.

**Why a separate integration child exists (not a padded verification child).** EP06H adds a **new Playwright spec suite** against the self-contained EP09 stack (`apps/web/e2e/study-plan.spec.ts`) that must pin a *date-dependent* 7-day rolling plan — the fixture must create availability, classes and assignments whose due dates land inside the generated window, and the assertions must be made against the window the server computed, not against wall-clock dates — plus the **parent implementation index**. That is real integration implementation and a substantial new test harness, not routine verification.

## Shared API and data contract

This is the seam between EP06A/EP06B/EP06C/EP06D (which implement it) and EP06E/EP06F/EP06G (which consume it) and EP06H (which verifies it end to end). Field names, bounds and status codes below are the stable part; the presentation is settled by the `ui-refiner` pass (D06-15).

### Data model (EP06D — one migration)

`StudyPlan` is kept as the per-day container (D06-3: the rolling week is seven per-day rows, `@@unique([userId, date])`). The legacy `ScheduledTask` model is reshaped into an **assignment-linked planned session** (D06-1, D06-2) and renamed, because "task" is materially wrong once the row references an `Assignment` and no longer references a `Task`:

```prisma
model StudyPlan {
  id          String   @id @default(uuid())
  userId      String
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  date        DateTime @db.Date
  targetHours Float    // Target study hours for this day
  notes       String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  sessions PlannedSession[]

  @@unique([userId, date])
  @@map("study_plans")
}

model PlannedSession {
  id          String   @id @default(uuid())
  studyPlanId String
  studyPlan   StudyPlan @relation(fields: [studyPlanId], references: [id], onDelete: Cascade)
  assignmentId String
  assignment  Assignment @relation(fields: [assignmentId], references: [id], onDelete: Cascade)
  startTime   DateTime
  endTime     DateTime
  durationMinutes Int
  status      PlannedSessionStatus @default(SCHEDULED)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([studyPlanId])
  @@index([assignmentId])
  @@map("planned_sessions")
}

enum PlannedSessionStatus {
  SCHEDULED
  IN_PROGRESS
  COMPLETED
  SKIPPED
  RESCHEDULED
}
```

- `Task.scheduledTasks` is removed; `Assignment` gains `plannedSessions PlannedSession[]`.
- `PlannedSession` has no `userId` of its own — it is scoped through `studyPlan.userId` (and, secondarily, `assignment.userId`). The ownership convention's header comment (`apps/api/src/common/ownership/ownership.ts:26-29`) names `ScheduledTask` and its parents and **must be updated in the same change** to name `PlannedSession` and `studyPlan.userId`.
- **Migration steps** (one migration folder, e.g. `apps/api/prisma/migrations/<timestamp>_study_plan_planned_sessions/migration.sql`). **The physical names are the schema's camelCase names** — no scalar field in `schema.prisma` carries an `@map`, so Prisma created the columns as `"studyPlanId"`, `"taskId"`, `"startTime"`, … (verified in the init migration: `apps/api/prisma/migrations/20261011000000_init/migration.sql:155-167` creates `"scheduled_tasks" ("id", "studyPlanId", "taskId", "startTime", "endTime", "durationMinutes", …)` and `:188` creates `CREATE UNIQUE INDEX "scheduled_tasks_studyPlanId_taskId_key"`). The steps below are **illustrative**; the authoritative SQL is derived with `prisma migrate diff` (the repo's convention) and must match these names **and apply in this order** — no statement may name an object that an earlier statement has already removed:
  1. `ALTER TABLE "scheduled_tasks" RENAME TO "planned_sessions";` — a table rename does **not** rename its indexes or constraints, so the unique index is still named `scheduled_tasks_studyPlanId_taskId_key` and the foreign keys are still `scheduled_tasks_studyPlanId_fkey` / `scheduled_tasks_taskId_fkey` at this point.
  2. `ALTER TYPE "ScheduledTaskStatus" RENAME TO "PlannedSessionStatus";` (the column default `'SCHEDULED'` is unaffected).
  3. `DROP INDEX "scheduled_tasks_studyPlanId_taskId_key";` — the unique index on `("studyPlanId", "taskId")`. **It is dropped *before* the column that owns it**, because PostgreSQL drops an index that involves a dropped column *together with* that column: a `DROP INDEX` after step 4 would abort with `index "scheduled_tasks_studyPlanId_taskId_key" does not exist` and the migration would not apply. (This is the order `prisma migrate diff` produces for a removed `@@unique` plus a removed column.)
  4. `ALTER TABLE "planned_sessions" DROP COLUMN "taskId";` — the FK constraint `scheduled_tasks_taskId_fkey` goes with the column (it was `ON DELETE RESTRICT`; the column's own `NOT NULL` goes too). After step 3 **no** index or constraint on the table references `"taskId"`, so nothing else is dropped implicitly.
  5. `ALTER TABLE "planned_sessions" ADD COLUMN "assignmentId" TEXT;` — then a **guard** that raises an exception if any row exists (`DO $$ BEGIN IF EXISTS (SELECT 1 FROM "planned_sessions") THEN RAISE EXCEPTION 'planned_sessions must be empty before the EP06 migration'; END IF; END $$;`) — then `ALTER TABLE "planned_sessions" ALTER COLUMN "assignmentId" SET NOT NULL;` and the FK to `assignments(id)` with `ON DELETE CASCADE` (constraint name `planned_sessions_assignmentId_fkey`).
     The guard is not defensive noise: the table is provably empty in every deployed environment (no API or web code references `StudyPlan`/`ScheduledTask` — see the code baseline), and a silent delete would destroy data if that were ever untrue.
  6. `CREATE INDEX "planned_sessions_studyPlanId_idx" ON "planned_sessions"("studyPlanId");` and `CREATE INDEX "planned_sessions_assignmentId_idx" ON "planned_sessions"("assignmentId");` — the names Prisma's `@@index([studyPlanId])` / `@@index([assignmentId])` produce.
- **Backfill:** none — there are no rows to backfill.
- **Rollback** (also ordered so that it applies; the reverse of the steps above):
  1. `DELETE FROM "planned_sessions";` — the EP06-created rows. The original table was empty, so the rollback loses nothing that existed before EP06.
  2. `DROP INDEX "planned_sessions_studyPlanId_idx"; DROP INDEX "planned_sessions_assignmentId_idx";`
  3. `ALTER TABLE "planned_sessions" DROP CONSTRAINT "planned_sessions_assignmentId_fkey";` then `ALTER TABLE "planned_sessions" DROP COLUMN "assignmentId";`
  4. `ALTER TABLE "planned_sessions" ADD COLUMN "taskId" TEXT NOT NULL;` then `ALTER TABLE "planned_sessions" ADD CONSTRAINT "scheduled_tasks_taskId_fkey" FOREIGN KEY ("taskId") REFERENCES "tasks"("id") ON DELETE RESTRICT ON UPDATE CASCADE;` then `CREATE UNIQUE INDEX "scheduled_tasks_studyPlanId_taskId_key" ON "planned_sessions"("studyPlanId", "taskId");` — the index is created **after** the column it indexes exists, and it keeps its original name because a rename never renames an index.
  5. `ALTER TABLE "planned_sessions" RENAME TO "scheduled_tasks";` then `ALTER TYPE "PlannedSessionStatus" RENAME TO "ScheduledTaskStatus";`
  The rollback is documented in EP06D's implementation record.
- `PlannedSessionStatus` keeps its five values so that EP08's miss detection has room; **EP06 only ever writes `SCHEDULED`**.

### The pure domain module

The epic's Technical Notes require the scheduling algorithm to be a pure TypeScript domain module, independent of HTTP, React and the database. It lives in `apps/api/src/domain/study-planning/` (a new top-level folder, deliberately outside `modules/`, so the "no Nest, no Prisma, no clock, no randomness" boundary is visible in the import graph):

| File | Contents |
|---|---|
| `types.ts` | `StudyPreferences`, `SchedulableAssignment`, `WeeklyWindow`, `DatedInterval`, `SchedulerInput`, `SchedulerOutput`, `PlannedSessionProposal`, `DeficitCategory` |
| `preferences.ts` | the `StudyPreferences` defaults, the bounds, the cross-field rules, the defensive reader and the validator |
| `intervals.ts` | the interval algebra: `mergeIntervals`, `subtractIntervals`, `overlaps`, `minutesBetween` — **and the one shared free-interval helper `freeIntervals(...)`** (the "available − blocked − classes − confirmed − already placed" subtraction, used by EP06C's placement and by EP06D's save-time re-check — its complete signature and semantics are in *The shared free-interval helper* below) |
| `ordering.ts` | **the one shared comparator** `compareAssignments(...)` (D06-22) — on-time first, then overdue, then undated; then due date ascending, priority descending, `createdAt` ascending, `id` ascending |
| `remaining-work.ts` | the remaining-work classification (`schedulable` vs `flagged`) and the estimate→minutes conversion |
| `scheduler.ts` | the deterministic placement engine |
| `*.spec.ts` | the unit tests (TR-E06-03) |

The module imports nothing from `@nestjs/*`, nothing from Prisma and reads no clock: the caller supplies "today" and every time window. The NestJS service retrieves the academic data, invokes the engine and persists the confirmed result through a Prisma transaction (the epic's Technical Notes, third paragraph).

### The shared free-interval helper `freeIntervals(...)` (EP06C owns it; EP06D calls it)

This is the **one** implementation of "when is a student free?" — the placement (EP06C) and the save-time re-check (EP06D) both call it, so the two cannot drift. Its complete contract:

```ts
// apps/api/src/domain/study-planning/intervals.ts  (EP06C)
// `DatedInterval` and `WeeklyWindow` are declared in `types.ts` (the shared types file).

/** A half-open [startMinute, endMinute) interval in wall-clock minutes from
 *  midnight, on one civil date. */
type DatedInterval = { date: string; startMinute: number; endMinute: number };

/** The base the day's free intervals are computed from. */
type FreeIntervalBase =
  | { kind: 'declared'; windows: DatedInterval[] }  // the student's declared available windows
                                                      // (AvailabilitySlot.isAvailable = true) for that weekday
  | { kind: 'whole-day' };                          // the whole civil day, [00:00, 1440)

function freeIntervals(input: {
  date: string;                       // the civil date ('YYYY-MM-DD') the free intervals are computed for
  base: FreeIntervalBase;             // 'declared' → the merged declared windows; 'whole-day' → [00:00, 1440)
  blocked: DatedInterval[];           // the recurring blocked windows (AvailabilitySlot.isAvailable = false)
  classes: DatedInterval[];           // the ClassMeeting windows of the student's active courses
  busy: DatedInterval[];              // the confirmed StudySession intervals
  placed: DatedInterval[];            // the sessions this run has ALREADY PLACED (the engine) or the OTHER
                                      // already-submitted sessions (the re-check)
}): DatedInterval[];                   // sorted, disjoint, half-open
```

- **Every input is filtered by `date`.** The helper keeps only the intervals whose `date` equals `input.date`, so a caller can hand it the whole week and cannot leak another day's windows into the result. `base.windows` is filtered the same way.
- **The base.** `base.kind === 'declared'` → the base is `mergeIntervals(base.windows)` — the student's **declared** available windows. An **empty** `windows` array means the student declared no availability for that weekday, so the day has no free time (the engine's `NO_AVAILABLE_TIME` case). `base.kind === 'whole-day'` → the base is the whole civil day, `{ date, startMinute: 0, endMinute: 1440 }`. **The 'whole-day' mode is the availability-omitted mode**: it exists because a *manual* edit is not bounded by the student's declared availability (D06-12). The two modes are **different values of one parameter**, never an omitted argument and never an empty array — so a caller can never accidentally mean "no availability" when it means "no bound".
- **The subtractions, in this order:** `base − blocked − classes − busy − placed`. Each list is subtracted with the shared `subtractIntervals`.
- **`placed` is required, never optional.** It is the input that makes the helper safe for both call sites: the engine passes the sessions it has already placed on that date in this run (so its second placement on a day cannot overlap its first), and the re-check passes the **other** submitted sessions on that date (the session under test is excluded from its own `placed` set — otherwise every submitted session would conflict with itself and every save would be rejected).
- **The result** is a sorted, disjoint list of half-open intervals; touching intervals are merged (`[09:00,10:00)` + `[10:00,11:00)` → `[09:00,11:00)`); `overlaps` treats touching intervals as **not** overlapping.
- **The helper is pure and zone-free.** It reads no clock, no database and no availability row: the caller selects the rows, converts the `HH:mm` strings to wall-clock minutes and dates them first.

**The two call sites, verbatim:**

| Call site | `base` | `placed` | What it decides |
|---|---|---|---|
| **EP06C's placement** (the engine) | `{ kind: 'declared', windows: <the student's declared available windows for that weekday> }` | the sessions the engine has already placed on that date in this run | where a session may be placed (AC-E06-03, AC-E06-04) |
| **EP06D's save-time re-check** | `{ kind: 'whole-day' }` — a manual edit is not bounded by the declared availability (D06-12) | the **other** submitted sessions on that date | whether a submitted session is legal at all; a session that is not wholly inside one of the day's free intervals is a conflict (409) |

**The conflict reason is attributed with the same module's `overlaps` primitive.** When the re-check's verdict fails, the conflict function attributes the reason by checking the session against each hard source with `overlaps(...)` — the same primitive the helper uses — in the stated precedence order `OVERLAPS_CLASS` → `OVERLAPS_BLOCKED_TIME` → `OVERLAPS_CONFIRMED_SESSION` → `OVERLAPS_PLANNED_SESSION` (see *The save, the edits and the conflict re-check*). The **verdict** therefore comes from the shared helper and the **reason** from the shared primitive: there is still no second implementation of the subtraction.

### The study-preferences shape (D06-4 — the final shape for seam V-07-1)

Stored in `User.preferences.studyDefaults`. The bag is validated today only as a plain object of bounded size (`apps/api/src/modules/users/dto/update-user.dto.ts:17-20`), so EP06 owns the concrete shape, its validation and its own endpoint.

```jsonc
{
  "studyDefaults": {
    "sessionLengthMinutes": 60,   // integer, 5..480  — the default session length (D06-4's "duration default")
    "minSessionMinutes": 15,      // integer, 5..480  — the shortest session the student wants
    "maxSessionMinutes": 120,     // integer, 5..480  — the longest session the student wants
    "dailyCapMinutes": 240        // integer, 5..1440 — the most planned minutes per day
  }
}
```

- **Defaults** (used when the bag is missing, when a key is missing, or when a key's value is invalid): `60 / 15 / 120 / 240`.
- **Cross-field rules:** `minSessionMinutes ≤ sessionLengthMinutes ≤ maxSessionMinutes`; `dailyCapMinutes ≥ minSessionMinutes`.
- **Read behaviour (defensive) — one ordered algorithm.** A missing, partial or malformed `studyDefaults` never fails a request and never yields an invalid value. The reader runs **these four steps in this order**, and every value it returns satisfies both cross-field rules:
  1. **Per-field bounds fallback.** For each of the four keys, the stored value is accepted only if it is an **integer inside that key's bounds** (`sessionLengthMinutes` / `minSessionMinutes` / `maxSessionMinutes`: `5..480`; `dailyCapMinutes`: `5..1440`). A missing key, a non-object bag, a wrong type (a string, a float, a boolean) or an out-of-range value falls back to **that key's own default** — the fields are independent at this step.
  2. **Repair the inverted min/max pair.** If `minSessionMinutes > maxSessionMinutes`, then `minSessionMinutes := maxSessionMinutes` (the maximum is kept and the minimum is lowered to it; the pair becomes degenerate but valid). This step runs **before** the session length is repaired, so the clamp in step 3 always has `min ≤ max`.
  3. **Clamp the session length.** If `sessionLengthMinutes < minSessionMinutes` then `sessionLengthMinutes := minSessionMinutes`; if `sessionLengthMinutes > maxSessionMinutes` then `sessionLengthMinutes := maxSessionMinutes`. (At most one of the two applies, because step 2 guarantees `min ≤ max`.)
  4. **Repair the daily cap.** If `dailyCapMinutes < minSessionMinutes` then `dailyCapMinutes := minSessionMinutes`.

  **Worked examples** (the stored bag → the four returned values):
  | Stored `studyDefaults` | Why | Returned |
  |---|---|---|
  | `null` / absent / not an object | step 1 | `60 / 15 / 120 / 240` |
  | `{ sessionLengthMinutes: 600, minSessionMinutes: 15, maxSessionMinutes: 120, dailyCapMinutes: 240 }` | step 1 (600 > 480) | `60 / 15 / 120 / 240` |
  | `{ sessionLengthMinutes: 60, minSessionMinutes: 300, maxSessionMinutes: 200, dailyCapMinutes: 240 }` | step 2 (300 > 200 → min := 200), then step 3 (60 < 200 → 200) | `200 / 200 / 200 / 240` |
  | `{ sessionLengthMinutes: 60, minSessionMinutes: 90, maxSessionMinutes: 120, dailyCapMinutes: 240 }` | every field is in bounds; step 3 raises the session length to the minimum | `90 / 90 / 120 / 240` |
  | `{ sessionLengthMinutes: 60, minSessionMinutes: 15, maxSessionMinutes: 120, dailyCapMinutes: 10 }` | step 4 (10 < 15 → 15) | `60 / 15 / 120 / 15` |

  The bag's **other** keys are never read and never written by EP06.
- **Write behaviour:** `PUT /study-preferences` accepts any subset of the four keys, merges it onto the **current effective** values and validates the merged result (the `availability` module's precedent — "validation runs on the merged values"), then writes the complete four-key object into `preferences.studyDefaults` and leaves every other key of the bag untouched.
- **V-07-1 (EP07's re-check) is now mechanical:** EP07 reads `User.preferences.studyDefaults.sessionLengthMinutes` as its session-duration default. EP06's default is **60 minutes**, so EP07's own fallback default must be 60 minutes to agree; and EP07's bounds check must accept `5 ≤ sessionLengthMinutes ≤ 480` (the same band EP07 already uses for `plannedMinutes`). **The value EP07 re-checks is the *effective* one** — the `sessionLengthMinutes` that `GET /study-preferences` returns, i.e. the per-field fallback and then the clamp of step 3 — and **not** the raw stored value. With no stored preferences it is exactly **60**; with the review's counterexample bag (`60 / 90 / 120 / 240`) it is **90**. EP07 must therefore read the effective value (from the endpoint, or by applying the same ordered algorithm) and must not re-derive it from the raw bag.

### The window, the dates and the time representation (D06-23, D06-24)

- **The server owns the window in both directions (D06-23).** The preview computes it (`today` … `today+6`, today = the civil date in the student's profile `timeZone`); the read states the window it used. **The client never derives a date from the browser's clock** — the FU-EP04-01 lesson — and never computes "today" itself.
  - **`GET /study-plans` with no query parameters** returns the **student's most recent saved plan window**, and the **current rolling window** when the student has never saved one. "Most recent saved plan window" = `[max(StudyPlan.date) − 6 days, max(StudyPlan.date)]` over the student's own rows (the save writes all seven per-day rows, so `max(date)` is the window's last day); when there are no rows the window is `[today, today+6]` and the response is empty. The response's `from`/`to` always state the effective window, so a fresh mount renders exactly the days the server used — a student who saved a plan on Monday and reopens the tab on Tuesday sees **that** week, not an empty one.
  - **`GET /study-plans?from&to`** returns the explicitly named range (the calendar/history view; the inclusive span ≤ 31 days, the `calendar` module's rule). Supplying only one of the two is a 400.
- **Every date EP06 returns is a civil date in the profile zone (D06-24).** `Assignment.dueDate` is stored as an **instant**; the service converts it **once**, to the civil date in the student's profile `timeZone` — the same conversion the calendar uses (`zoneDateParts`, `apps/api/src/modules/calendar/calendar.service.ts:47-66`), so an assignment due `2026-11-01T00:30:00Z` is **31 October** for a student in `America/New_York` and is placed and reported as 31 October. The engine's due-date input is a civil `YYYY-MM-DD` **string**, never an instant (D06-24); the horizon and the overdue test compare civil dates (`YYYY-MM-DD` sorts chronologically as a string).
- **The time representation is wall-clock `HH:mm` + a civil date, in both directions.** The preview returns `"startTime": "09:00"`; the save accepts `"09:00"`; the read returns `"09:00"` again. The **write-side conversion** is the server's: `date` + `HH:mm` in the profile zone → the persisted instant (the calendar service's `wallToInstant` arithmetic, `:105-132`), and the read converts the stored instants back to `HH:mm` in the profile zone (`zoneDateParts`, `:47-66`). `durationMinutes` is **derived server-side** from the range (`endTime − startTime`, same day) and is never accepted from the client (see the save body below). An `HH:mm` value means an hour in `00`–`23` and a minute in `00`–`59`; `24:00` is **not** a valid time and is rejected by the malformed-session matrix.
- **The weekday of a civil date.** `AvailabilitySlot.dayOfWeek` and `ClassMeeting.dayOfWeek` are `0`–`6` with **Sunday = 0** (the schema's own comments, `apps/api/prisma/schema.prisma:292-305` and `:167-181`; the availability API's validation message says "0 (Sunday) … 6 (Saturday)", `apps/api/src/modules/availability/availability.service.ts:99`). The weekday of a civil `YYYY-MM-DD` date is `getUTCDay()` on that date's UTC midnight — the calendar's own `dayOfWeekOf` (`apps/api/src/modules/calendar/calendar.service.ts:83-85`), which it uses to pick the class meetings (`:229-232`) and the availability slots (`:253`). EP06 uses the same mapping, so a window day that falls on a Sunday uses the Sunday windows. The date→weekday mapping is the **caller's** job (the service builds the window; the engine expands the weekly windows into dated intervals), so the engine itself stays zone-free and clock-free (D06-17).

**`targetMinutes` and `StudyPlan.targetHours` are the same quantity in two units.** The payloads expose the day's planned time as **`targetMinutes`** (an integer); the stored column is **`StudyPlan.targetHours`** (a `Float`, in hours). ### The engine's rules

1. **Window (D06-3).** The plan covers the next **7 days starting today**, where "today" is the civil date in the student's profile `timeZone`. The seven dates are `[today, today+6]`. The **generation** window is fixed — the preview takes no window input — and the save may name only a window the server could itself have generated (D06-21).
2. **Order (AC-E06-05, D06-9, D06-22).** Assignments are processed in a fully deterministic order, given by **one comparator** that the engine and the remaining-work read share (`apps/api/src/domain/study-planning/ordering.ts`): **on-time assignments first** (due date ascending), then **overdue assignments** (due date before today), then **undated** assignments (a null due date — always a flagged assignment, so the engine never places one); within a group by priority descending (`URGENT` > `HIGH` > `MEDIUM` > `LOW`), then by `createdAt` ascending, then by `assignmentId` ascending. The last key makes the order total — no two runs can differ. The comparator compares **civil dates** (D06-24): "on time" means "its civil due date ≥ today's civil date in the profile zone".
3. **Free intervals (AC-E06-03, AC-E06-04).** For each date in the window, the day's free intervals are computed by **one shared helper** — `freeIntervals(...)` in `apps/api/src/domain/study-planning/intervals.ts` (EP06C) — whose **complete signature and semantics are in *The shared free-interval helper* above**. In one line: the student's **available** `AvailabilitySlot` windows for that weekday (the `base`), minus the **blocked** `AvailabilitySlot` windows (`isAvailable: false`), minus the `ClassMeeting` windows of active courses, minus the confirmed `StudySession` intervals, minus **the sessions this run has already placed** (the helper's required `placed` input). The **save-time re-check in EP06D calls the same helper** with `base: { kind: 'whole-day' }` — the availability-omitted mode, because a manual edit is not bounded by the student's declared availability (D06-12) — and passes the **other submitted sessions** in `placed`, so the two call sites cannot drift and neither can silently lose the "already placed" sessions. All of it is computed in the profile zone's wall-clock minutes; the service converts the confirmed sessions to wall-clock intervals and dates the weekly windows before calling the engine.
4. **Daily cap (D06-20).** The total planned minutes on a day may not exceed `dailyCapMinutes`. The day's remaining budget starts at `dailyCapMinutes` and is decremented by each placed session on that date; the budget is consumed in interval order, so the cap binds deterministically. **The cap truncates a session; it never causes a session to be skipped** (see rule 5). The cap is a **generator** rule — it bounds what the generator places and is not enforced against a manual edit (D06-12).
5. **Session length (D06-20 — one arithmetic).** For each placement:
   ```text
   desired = min(sessionLengthMinutes, remainingWork)   // the length the work wants
   budget  = the date's remaining daily budget           // starts at dailyCapMinutes
   length  = min(desired, budget)                        // the cap truncates; it never skips
   ```
   - If `length ≥ minSessionMinutes`, a session of `length` minutes is placed.
   - If `length < minSessionMinutes`, a **short session** of `length` minutes is placed anyway: `length` is then either the assignment's remaining tail (`desired < minSessionMinutes` — the tail rule) or the day's remaining budget (`budget < minSessionMinutes` — the cap's remainder). `minSessionMinutes` is a preference for the *typical* session, not a floor that would waste the student's remaining minutes; the tail and the cap are the only two reasons a session may be shorter.
   - A session is only placed in an interval that fits its whole length (no splitting a session across two intervals); an interval that is too short for it is left unused, and the unused capacity shows up in the deficit report.
   - **The deficit** for an on-time assignment is `max(0, remainingWork − placedMinutes)` over its horizon (rule 7). The minutes the cap truncated **were placed** and are therefore **not** a deficit.

   **Worked example.** `dailyCapMinutes = 100`, one available window 09:00–12:00 on day 1, one assignment of 200 minutes, `sessionLengthMinutes = 60`, `minSessionMinutes = 15`, no free time on days 2–7. Day 1, first interval: `desired = min(60, 200) = 60`, `budget = 100` → `length = 60` → a 60-minute session; `budget = 40`, remaining work 140. Day 1, second interval: `desired = 60`, `budget = 40` → `length = 40` → a 40-minute session (≥ 15, so an ordinary session); `budget = 0`, remaining work 100. The budget is exhausted, so nothing more is placed on day 1. **Placed: 100 minutes. Deficit (`INSUFFICIENT_TIME_BEFORE_DEADLINE`): 100 minutes.** No minute of the student's declared cap is wasted and no minute of the work is double-counted.
6. **Splitting across days (D06-2).** One assignment's remaining work may be placed in several sessions, on several days, inside the window — that is the "spread my work across the week" behaviour.
7. **Deadline horizon.** An on-time assignment is placed only on dates `≤ its due date` (both are civil dates, compared lexicographically — `YYYY-MM-DD` sorts chronologically). Work that cannot be placed before the due date is reported as `INSUFFICIENT_TIME_BEFORE_DEADLINE` with the minutes from rule 5; an assignment with no free time at all in the window is reported as `NO_AVAILABLE_TIME`.
8. **Overdue.** An assignment whose **civil** due date is before today's civil date in the profile zone is still placed, but **after** every on-time assignment (so it never takes capacity an on-time assignment needs), and it is reported as `OVERDUE` with its full remaining minutes. The report is factual and blame-free (EP08's principle).
9. **Deferred.** Work that is not placed but whose deadline lies beyond the window is reported as `deferred` (it continues in a later plan), not as a deficit.
10. **Flagged (AC-E06-09, D06-25).** An assignment with no `estimatedHours` (or a non-positive one) or no `dueDate` is **flagged** (`MISSING_ESTIMATE` / `MISSING_DUE_DATE`) and never scheduled. Both fields are "necessary scheduling information": the epic's ACs are assignment-centric over "assignment estimates and due dates", and without a deadline the capacity-before-deadline question cannot be answered at all.
11. **Unfinished only.** Assignments whose status is `COMPLETED`, `SUBMITTED` or `GRADED` are not candidates.
12. **No due-date writes (AC-E06-08).** The engine has no write path at all; the service writes only `StudyPlan` and `PlannedSession` rows. `Assignment.dueDate` — and every other assignment field — is never written by EP06.

### The save, the edits and the conflict re-check (D06-5)

- The preview is a **proposal held by the client**; the student may move, resize and delete a proposed session in the preview. There is **no free-form session creation** — the epic does not require it, so no create affordance is built. (The save endpoint accepts the edited session list, so a crafted request could introduce a session; that is not reachable through the product, and the endpoint still validates every submitted session against the rules below. The rule is a **scope** rule, not a security invariant — see D06-12.)
- **The save body (D06-21).** `{ from, to, sessions: [{ assignmentId, date, startTime, endTime }] }`:
  - `from` / `to` are the `YYYY-MM-DD` window the **preview** returned (`to` is exactly six days after `from`); they are the window the student actually reviewed and edited.
  - `date` is the civil date of the session; `startTime` / `endTime` are `HH:mm` wall-clock times **in the student's profile zone** — the same representation the preview returned, so the client converts nothing.
  - **Exactly these four fields are accepted.** `durationMinutes` and `assignmentTitle` are response-only; the global `FieldValidationPipe` runs with `whitelist: true, forbidNonWhitelisted: true` (`apps/api/src/test/test-http.ts:97-106`), so a client that posts a preview session unchanged gets a 400 — the client **projects** each session onto the four fields.
  - **The duration is derived server-side** from the range (`endTime − startTime`, same day) and is written to `PlannedSession.durationMinutes`. It can therefore never disagree with the range, which is why the malformed matrix has **no** "a duration that does not match the range" case: with no duration field, that check would be unreachable text.
  - **The write-side conversion:** `date` + `HH:mm` in the profile zone → the persisted instant (the calendar service's `wallToInstant` arithmetic, `apps/api/src/modules/calendar/calendar.service.ts:105-132`); the read converts the stored instants back to `HH:mm` in the profile zone (`zoneDateParts`, `:47-66`).
- **The save is atomic.** `POST /study-plans` upserts the seven `StudyPlan` rows for the named window, deletes the window's existing `PlannedSession` rows and inserts the submitted ones, in **one Prisma transaction**. A failure rolls the whole thing back; a partially replaced week is never persisted.
- **The window and the rollover (D06-21).** The server recomputes "today" at save time. The named window must be one the server could itself have generated: `from` must lie within the last seven rolling windows (`today − 6 ≤ from ≤ today`). A midnight rollover between the preview and the save is therefore **not** an error — the student saves the exact week they reviewed, manual edits included. A window older than that is **409** `{ error: 'WINDOW_ROLLED_OVER', message: 'The plan week has rolled over — generate a new proposal to save it.' }` and nothing is written; the client turns that code into the actionable "the week has rolled over — generate a new plan" message and the generate action (the manual edits are then lost — FU-EP06-01's recorded consequence).
- **Conflicts are re-checked on save (D06-5).** Every submitted session is re-validated against the current state:
  - a malformed session (a date outside the named window, a date that is not `YYYY-MM-DD`, a time that is not `HH:mm` — an hour outside `00`–`23` or a minute outside `00`–`59` — a non-increasing time range, a missing/blank assignment id) → **400** with a field-level `errors` map;
  - an assignment that is not the student's → the **uniform 404** `Resource not found`;
  - an overlap with a class, a blocked window, a confirmed session or another submitted session → **409** with a `conflicts` array naming each offending session (`sessionIndex`, `date`, `startTime`, `reason`).
  - **The `reason` vocabulary — exactly four codes, no others.** One entry per offending session; when a session conflicts with more than one source, the entry carries the **highest-precedence** reason in the order below. These four codes are the **shared contract**: EP06D's `findConflicts` emits exactly these values and EP06F maps them to student-facing wording.

    | `reason` | The submitted session overlaps… |
    |---|---|
    | `OVERLAPS_CLASS` | a `ClassMeeting` window of one of the student's active courses |
    | `OVERLAPS_BLOCKED_TIME` | a recurring blocked window (`AvailabilitySlot.isAvailable = false`) |
    | `OVERLAPS_CONFIRMED_SESSION` | a confirmed `StudySession` interval |
    | `OVERLAPS_PLANNED_SESSION` | another submitted session in the same save |
  - The re-check computes the day's hard-conflict-free intervals with **EP06C's `freeIntervals` helper** (`apps/api/src/domain/study-planning/intervals.ts`) — called with `base: { kind: 'whole-day' }` (the availability-omitted mode: a manual edit is not bounded by the student's declared availability — D06-12) and with `placed` = the **other submitted sessions** on that date. A submitted session is legal only if it lies **wholly inside** one of the resulting free intervals; otherwise it is a conflict. The **verdict** therefore comes from the shared helper and the **reason** from the same module's `overlaps` primitive — the placement and the re-check cannot drift.
- **Manual edits are bounded by the hard conflicts only.** A moved or resized session must not overlap a class, blocked time, a confirmed session or another planned session. The **availability window** and the **daily cap** are *generator* rules: a student may deliberately study outside their declared availability, so a manual edit is not rejected for that (D06-12).
- **Replace semantics (D06-13).** A save replaces exactly the sessions whose date falls inside the **named** window `[from, to]`. Sessions outside that window (including a previous window that has since rolled forward) are untouched and remain readable through `GET /study-plans?from&to`. **A planned session has no `date` of its own** — the civil date lives on the parent `StudyPlan` row (`StudyPlan.date`, the per-day container) — so the replace scope is selected **through the owned plan row**: `tx.plannedSession.deleteMany({ where: { studyPlan: { userId, date: { gte: fromDate, lte: toDate } } } })` (the Prisma relation filter; `fromDate`/`toDate` are the window's `from`/`to` civil dates converted to UTC-midnight `Date` values, the `@db.Date` convention — the same value the `StudyPlan.upsert` uses). The same filter carries the ownership scoping (`studyPlan.userId`), so it can only ever touch the student's own rows.

### Rules

1. **Ownership.** Every query carries the authenticated student's `userId` (`ownedWhere` / `assertOwned` / `assertAffected`, `apps/api/src/common/ownership/ownership.ts`). A missing or a foreign record returns the same uniform 404 `Resource not found` — never 403, never a distinct message (no existence oracle). `PlannedSession` is scoped through `studyPlan.userId`.
2. **The scheduler schedules assignments (D06-1).** A planned session references an `Assignment`. Subtasks stay EP03's checklist and are never scheduled.
3. **Confirmed time comes from the session log (D07-2 honoured).** `Assignment.actualHours` and `Task.actualMinutes` are **never read** as confirmed time (no API writes them today, and `PATCH /assignments` rejects `actualHours` as a lifecycle field). EP06 aggregates the `StudySession` log itself (D06-6).
4. **Remaining work (AC-E06-02).** `remainingMinutes = max(0, round(estimatedHours × 60) − confirmedMinutes)`.
5. **EP06 owns its confirmed-time read (D06-6).** EP06 reads `StudySession` directly through its own ownership-scoped aggregation and does **not** consume EP07B's `GET /study-sessions/confirmed-time` (seam V-07-2). This keeps EP06 and EP07 parallel in M3. EP07's endpoint remains authoritative for EP07's own surfaces.
6. **Purity.** The engine is a pure function: no clock, no randomness, no database, no HTTP. The same inputs always produce the same plan (AC-E06-05's determinism).
7. **The assignment's due date is never changed (AC-E06-08).**
8. **Flagged work is never silently scheduled (AC-E06-09).**
9. **Errors are actionable.** 400 carries a field-level `errors` map; 404 is the uniform `Resource not found`; 409 carries a human-readable reason and, for the save, the per-session `conflicts` array.
10. **The plan is one review unit.** No child is independently released; the combined EP06 review is the gate.
11. **The window and every date are the server's (D06-23, D06-24).** The client never derives a date from the browser's clock; the read states the window it used, and every date EP06 returns is a civil date in the student's profile `timeZone`.
