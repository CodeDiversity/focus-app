## Findings in detail

### PR-023 — Polish — The shared domain types are given two different homes

- **Requirement/source:** the shared API/data contract must be internally consistent (the planning checklist's contract-consistency row); `.agents/story-sizing.md`'s required sizing block ("Start context: … exact shared contract sections"); EP06A's implementation notes.
- **Observed gap:** the contract's module table assigns `StudyPreferences` to `types.ts` (`README.md:194`) while the next row describes `preferences.ts` as holding "the `StudyPreferences` defaults, the bounds, the cross-field rules, the defensive reader and the validator" (`:195`) — the **type** itself is placed ambiguously. EP06A's implementation note 1 resolves it the other way: `preferences.ts` "exports `STUDY_PREFERENCE_DEFAULTS`, `STUDY_PREFERENCE_BOUNDS`, **`type StudyPreferences`**, `validateStudyPreferences(...)` and `readStudyPreferences(...)`" (`EP06A…md:91`), and EP06A's file list carries **both** `preferences.ts` (new) and `types.ts` (new — the shared types) (`:136-137`). The same pattern recurs in the helper's code block: its header names `intervals.ts` and its comment says "`DatedInterval` and `WeeklyWindow` are declared in `types.ts`", yet the block itself declares `type DatedInterval = { date: string; startMinute: number; endMinute: number }` (`README.md:208-214`).
- **Concrete consequence / counterexample:** an EP06A implementer following the contract's module table puts the `StudyPreferences` type in `types.ts` and its runtime helpers in `preferences.ts`; an EP06A implementer following EP06A's note puts the type in `preferences.ts`. EP06C then adds `SchedulerInput` to `types.ts` and must import `StudyPreferences` from somewhere — the plan never says which. Because TypeScript is structurally typed the two declarations remain mutually assignable, so nothing fails to compile and no test fails; the cost is a duplicated declaration and an import path that differs between the contract and the child.
- **Suggested correction:** state one home per type. Either move `StudyPreferences` out of the `types.ts` row of the module table (leaving the runtime helpers there) and drop the inline `DatedInterval` declaration from the contract's code block (keeping the comment that it lives in `types.ts`), or declare it once in `types.ts` and have `preferences.ts` import it. One sentence in the contract's module table settles it for every child.
- **Acceptance condition:** every shared type named in the contract has exactly one declared home, and the contract's code blocks contain no declaration that the contract's own module table assigns elsewhere. The children's files and the contract agree.

### PR-024 — Polish — The migration has two authorities, and the named one cannot produce the documented migration

- **Requirement/source:** EP06D AC 1 ("the migration's rollback step is documented and reversible"), DoD 9 ("API changes and migrations are documented"), and the planning checklist's operational/data-changes checks ("migration order, rollback/recovery strategy").
- **Observed gap:** the contract says the step list is "**illustrative**; the authoritative SQL is derived with `prisma migrate diff` (the repo's convention) and must match these names **and apply in this order**" (`README.md:170`), and EP06D repeats it: "The authoritative SQL is derived with `prisma migrate diff` (the repo's convention) and must match these names" (`EP06D…md:108`). But the documented migration is a **rename** migration — `ALTER TABLE "scheduled_tasks" RENAME TO "planned_sessions"` and `ALTER TYPE "ScheduledTaskStatus" RENAME TO "PlannedSessionStatus"` (`README.md:171-172`) — and Prisma's diff engine does not emit `RENAME` statements: a changed `@@map` is modelled as a drop plus a create. The plan's own argument for the guard is that "a silent delete would destroy data if that were ever untrue" (`README.md:176`), which is precisely what a diff-generated `DROP TABLE` would do, guardlessly.
- **Concrete consequence / counterexample:** an EP06D implementer who runs the repo's stated derivation (`prisma migrate dev`, which uses the diff engine) gets `DROP TABLE "scheduled_tasks"` + `CREATE TABLE "planned_sessions"` — a destructive statement with **no guard**, a different forward migration from the one the plan documents, and a forward migration the documented five-step rollback (which renames the table back and re-adds `"taskId"`) was not written against. The plan's own mandatory migration check resolves the conflict in practice — it requires that "the guarded `"assignmentId"` step succeeds on the empty table" (`EP06D…md:92`) — so a compliant implementer ends up hand-writing the documented SQL, but nothing in the plan says so.
- **Suggested correction:** name the documented rename-based SQL as **the** artifact and demote `prisma migrate diff` to what it can actually contribute (the column, index and FK names), with one sentence such as: "the diff engine cannot express a table or enum rename, so the forward migration is hand-written in the order below; `prisma migrate diff` is used only to confirm the column/index/constraint names." Note in the same place that the diff-derived form would be a destructive `DROP TABLE` and is **not** acceptable here because the guard must survive.
- **Acceptance condition:** the plan states one authoritative forward migration, and the derivation instruction cannot be read as authorising a destructive `DROP TABLE` that drops the guard.
- **Evidence note:** `prisma migrate diff` / `prisma migrate dev` were **not** executed in this review (no shell in the reviewer runtime); the premise is Prisma's documented diff behaviour, not an execution here.

### PR-025 — Polish — EP06A's "preserved byte-for-byte" is not achievable for a `jsonb` column

- **Requirement/source:** EP06A AC 3 ("the other keys of the student's `preferences` bag are preserved byte-for-byte"); DoD 8 (the business rules have automated tests).
- **Observed gap:** the `preferences` column is `JSONB`: `apps/api/prisma/migrations/20261017141608_user_time_zone_preferences/migration.sql:2` — `ALTER TABLE "users" ADD COLUMN "preferences" JSONB`. PostgreSQL's `jsonb` stores objects with normalized (length-then-bytewise) key order and does not preserve the input's key order.
- **Concrete consequence / counterexample:** the bag written by EP03's own integration spec is `{ theme: 'dark', studyDefaults: { sessionLengthMinutes: 45 } }` (`apps/api/src/modules/users/users-profile-integration.spec.ts:147-150`). After a `PUT /study-preferences` writes `{ ...bag, studyDefaults: merged }`, the stored `jsonb` re-orders the keys (`studyDefaults` before `theme`), so an implementer who writes the AC's wording literally — comparing `JSON.stringify(stored)` with the original literal — gets a **spurious failure** on a bag whose values are perfectly intact. The substance (the other keys survive) is correct; only the phrase is wrong.
- **Suggested correction:** reword AC 3 to "the other keys of the student's `preferences` bag survive the write unchanged **in value** (PostgreSQL's `jsonb` does not preserve object key order, so compare the parsed values, not the serialized bytes)", and align EP06A's test bullet ("the stored `preferences` column still carries the student's unrelated keys after a `PUT`") — which already compares values, not bytes.
- **Acceptance condition:** no EP06A acceptance criterion or test obligation requires byte-for-byte equality of a `jsonb` document.

### PR-026 — Polish — The "no overlapping sessions" invariant states no competing-request counterexample

- **Requirement/source:** the shared planning validation's consistency-invariant check ("For every claimed **security or consistency invariant**, give a concrete counterexample: competing requests or a malicious/invalid input, the mechanism that prevents the failure, the expected losing request or rollback, and the owning child test").
- **Observed gap:** the invariants table's row "A saved plan contains no overlapping sessions" gives the counterexample "The student saves two sessions at the same time, or moves a session onto a class, a blocked window or a confirmed session" and the mechanism "the conflict re-check on save rejects the whole save with 409 …; the transaction never persists a partially conflicting plan" (`README.md:517`). The counterexample is a **single request** containing two overlapping sessions. The plan records no statement about **two competing saves**.
- **Concrete consequence / counterexample:** the save is a read-modify-write: the conflict re-check runs *before* the transaction (EP06D note 7, `EP06D…md:174`) and the replace happens *inside* it (`:153-165`). Two saves of the same window that overlap in time both pass the re-check; the second transaction's `deleteMany` cannot see the first's uncommitted inserts under PostgreSQL's default READ COMMITTED isolation, so both sets of rows can land and the persisted week contains two overlapping sessions. The window is still atomic (all of one save or none of it), so the invariant's "never persists a partially conflicting plan" is not violated — but the invariant's headline claim ("a saved plan contains no overlapping sessions") is not guaranteed against a self-race.
- **Suggested correction:** one sentence, either a mechanism or a recorded boundary. A mechanism: re-check inside the transaction after taking a per-student row lock on the window's `StudyPlan` rows, so the second save serializes behind the first and then sees the first's rows. A recorded boundary: "the re-check and the replace are not serialized against a concurrent save of the same window; two simultaneous saves can leave overlapping sessions (an MVP limitation, recorded, not a claimed guarantee)". Either way the invariant row should name the counterexample it does *not* cover.
- **Acceptance condition:** the invariants table states the concurrency boundary explicitly — a mechanism with an owning test, or a recorded limitation — so the claim and the guarantee agree.

- **Suggested correction:** either add the two cases to EP06H's scenario list (an empty-week journey and the journey at a phone viewport), or reword EP06H's DoD rows 5 and 7 to point at the children's own coverage ("the empty state and the narrow-screen pass are EP06F's/EP06G's; this suite exercises the conflict path and the empty-plan response"). Either edit makes the rows and the list describe the same behaviour.
- **Acceptance condition:** every DoD row in EP06H's list is matched by a scenario in its own test list, or explicitly points at the child that owns it.

### PR-028 — Polish — The children's `Refined:` fields contradict the queue's readiness
