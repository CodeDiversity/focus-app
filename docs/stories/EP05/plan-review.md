### PR-002 — The "26-hour IANA offset spread" exemplar is factually wrong for current tzdata, and the mandated adversarial test inherits the error (Should-fix)

- **Requirement / source:** shared planning validation — "Proposed implementation references real inspected code or is explicitly marked as new/proposed"; "For every claimed security or consistency invariant, give a concrete counterexample … the mechanism that prevents the failure"; EP05A AC #2 and its test obligation.
- **Original claim / gap:** the README's request-window bullet (`README.md:134`), D05-6 (`:207`), the invariants row (`:247`) and PC-EP05-01's Correction column (`:260`) all state: "the maximum UTC-offset spread in the IANA database is **26 hours** (UTC−12 `Etc/GMT+12` / Baker Island ↔ UTC+14 `Pacific/Kiritimati`) … both are permanent, non-DST zones, so the pair is realizable in practice". EP05A repeats it in AC #2 (`EP05A-…md:47`), design decision #3 (`:90`), the "IANA offset bound" fact (`:79`) and the mandatory adversarial test case (`:55`).
- **File / section / line:** as above; the affected test obligation is `apps/web/src/features/dashboard/model/dashboardRange.test.ts` ("Adversarial zone pair (required — the 26-hour spread)").
- **Consequence / counterexample:** in current tzdata **`Pacific/Kiritimati` is UTC+13:00** — it used UTC+14:00 only from 1995-01-01 to 1996-12-31. The only +14:00 zone is the fixed-offset pseudo-zone `Etc/GMT-14`, and a *student-selectable* profile zone can never be `Etc/GMT-14`: the zone picker uses `Intl.supportedValuesOf('timeZone')` (`apps/web/src/shared/lib/datetime.ts:165-179`), which returns canonical location zones only. So the mandated test, written as specified, either (a) hard-codes a fictional "+14 `Pacific/Kiritimati`" and thereby encodes a false technical claim in the permanent test suite, or (b) resolves the zones through `Intl` and silently exercises a **25-hour** spread (browser `Etc/GMT+12` −12 vs profile `Pacific/Kiritimati` +13) while its name, comment and assertion message claim 26 hours. Neither form tests what the plan says it tests.
  The **window size itself is unaffected** and remains correct: a 25-hour spread still admits a two-civil-day difference (e.g. browser `Etc/GMT+12` at 2026-01-01T20:00Z is civil 2026-01-01, profile `Pacific/Kiritimati` is civil 2026-01-02), so ±2 days is still required and ±1 day is still insufficient; the bound the argument needs is only "|offset spread| < 48 h". The defect is the **premise**, not the conclusion.
- **Suggested correction:** state the bound precisely — "the largest offset spread between any two zones in the tz database is 26 h, realized only by the fixed-offset pair `Etc/GMT+12` (−12) ↔ `Etc/GMT-14` (+14); the largest *location* zone today is +13 (`Pacific/Kiritimati`, `Pacific/Apia`, `Pacific/Tongatapu`), so the worst realistic pair — a browser at `Etc/GMT+12` with a `Pacific/Kiritimati` profile — spreads 25 h and can still place the two civil dates two days apart". Rewrite the adversarial case to build from **real zone ids at a chosen instant** (or from explicitly injected offsets) so that the two civil dates demonstrably differ by two days, and assert the **property** — the server-echoed `result.today` lies inside `[from, to]` — rather than a zone/offset label. The implementer must confirm the offsets with a bounded command (e.g. `Intl.DateTimeFormat('en-US', { timeZone, timeZoneName: 'longOffset' })`) and record the output, instead of trusting a name/offset pair quoted in the plan.
- **Acceptance condition for closure:** the README (request-window bullet, D05-6, invariants row, PC-EP05-01) and EP05A (AC #2, design decision #3, the `dashboardRange.test.ts` obligation) name a realizable zone pair with offsets verified by a recorded command; the test asserts the containment property in both directions; the ±2-day window size and the `result.today` selection key are unchanged.
