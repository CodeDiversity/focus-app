### PR-002 — The "26-hour IANA offset spread" exemplar and the mandated adversarial test (Should-fix, disputed in pass 1 → **Resolved**)

**Acceptance condition (pass 1):** the README (request-window bullet, D05-6, invariants row, PC-EP05-01) and EP05A (AC #2, design decision #3, the `dashboardRange.test.ts` obligation) name a realizable zone pair with offsets verified by a recorded command; the test asserts the containment property in both directions; the ±2-day window size and the `result.today` selection key are unchanged.

**Pass 1's premise was itself wrong, and this pass confirms that.** Pass 1 asserted "`Pacific/Kiritimati` is UTC+13:00 — it used UTC+14:00 only from 1995-01-01 to 1996-12-31", and that the only +14 zone was the fixed-offset pseudo-zone `Etc/GMT-14`. That is not the case in current tzdata. Independently re-verified this session against a remote tzdata service (provenance below):

| Zone | Offset (verified) |
|---|---|
| `Pacific/Kiritimati` | **+14:00** (50400 s, no DST) |
| `Etc/GMT+12` | **−12:00** (−43200 s) |
| `Pacific/Midway` | −11:00 |
| `Pacific/Niue` | −11:00 |
| `Pacific/Pago_Pago` | −11:00 |
| `Pacific/Tongatapu` / `Pacific/Apia` | +13:00 |
| `Pacific/Auckland` | +13:00 (October 2026, DST) |
| `Pacific/Chatham` | +13:45 (October 2026, DST) |
| `Pacific/Marquesas` | −9:30 |

So: the **maximum** offset among IANA location zones is **+14** (`Pacific/Kiritimati`) and the **minimum** is **−11** (`Pacific/Midway`/`Niue`/`Pago_Pago`) → worst **picker-to-picker** spread **25 h**; and the maximum spread across **any** two IANA zones is **26 h** (`Etc/GMT+12` −12 ↔ `Pacific/Kiritimati` +14). This **corroborates** the coordinator's and the planner's recorded `Intl` outputs and **refutes** pass 1's premise. The planner's decision not to change the rule was correct.

**The rule and its arithmetic now hold, and the plan states them precisely.**

- Window: browser-local civil date **± 2 days** (5 days inclusive), unchanged (`README.md:140`, `:234`, `:276`; `EP05A:47`, `:90`).
- Selection key: the server-echoed `result.today`, unchanged (`README.md:141`).
- Arithmetic: |Δ| ≤ 26 h < 48 h ⇒ the civil-date difference is ≤ 2 days ⇒ the profile zone's civil date lies within ±2 days of the browser's ⇒ the ±2-day window contains it for every legal offset pair. Verified by construction: the server interprets `from`/`to` in the **profile** zone (`calendar.service.ts:88-89` `rangeStartInstant` via `wallToInstant(..., timeZone)`, `:181-186` the zone from the stored profile row) and buckets events by the profile zone's civil date (`formatToday(timeZone)` at `:68-75`), so containment of the profile civil date is exactly containment of `result.today`. A 26 h spread is realizable with a two-day civil difference (browser `Etc/GMT+12` local 2026-01-01T23:00 → UTC 2026-01-02T11:00 → `Pacific/Kiritimati` 2026-01-03T01:00 ⇒ civil dates two days apart), which is why ±1 day is insufficient and ±2 days is required. 5 ≤ the API's 31-day inclusive cap (`calendar.service.ts:159-179`); `from === to` is legal (`:167`).
- The adversarial test obligation was rewritten exactly as pass 1 asked: `EP05A:55` — "build the case from **real zone ids at a chosen instant** … and assert the **containment property**, not the label: the server-echoed `result.today` lies **inside** `[from, to]`. Cover both directions of the spread … The implementer must first confirm the offsets with a bounded command … and **record the output** … A test that hard-codes '+14' for a zone that is not +14 fails the plan's own evidence rule." Echoed in `EP05A:47`, `:78`, `:90`, `:127`, `README.md:140`, `:234`, `:276`, and PC-EP05-05 (`README.md:302`).
- **The plan's own evidence rule is now honest**: the offsets are stated as "verified by command (2026-10-30, PC-EP05-05)" with the command and its output recorded, and the implementer is required to re-verify and record it. The 26 h / 25 h bound does **not** depend on the unverified "418 zones, no `Etc/*`" count: it needs only the max location offset (+14), the min location offset (−11) and the browser's possible OS zone (`Etc/GMT+12`, −12) — all three independently verified above. (The `Intl.supportedValuesOf` list is only used to distinguish the 26 h "any two zones" bound from the 25 h "picker-to-picker" bound; the ±2-day window follows from either.)

**Disposition: resolved.** The plan's rule was correct and is unchanged; the premise error was in pass 1; the correction made the bound precise, recorded the verifying command and adopted the containment-property test obligation.
